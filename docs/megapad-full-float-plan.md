# Megapad full floating point: plan

**Started:** 2026-09-29

**Status:** Phase 1 complete. Decisions D1–D18 were confirmed on
2026-09-29 and are recorded in `docs/floating-point.md`, which is now the
normative floating-point specification. Phase 2 is next. No backend code has
changed yet.

**Branch:** `feature/megapad-fp64`

**Isolated worktree:** `../megapad-fp64`, a sibling of the main checkout, so
this work does not disturb the simulator speed work on `main`.

**Base:** `0cfece4`

## 1. Purpose

MegaPad gains complete IEEE 754 floating point:

- FP32 and FP64 tile formats beside FP16 and BF16;
- a scalar FP32/FP64 unit in the CPU that works directly on the 64-bit GPRs;
- one bit-exact definition of every floating-point result, shared by the
  Python emulator, the native accelerator, the hosted simulator, and the RTL.

Data analysis and numerically sensitive scientific code need binary64. FP32
gives 16 tile lanes and covers most bulk work. Today Akashic has FP16 on the
tile engine and a pure-software binary32 library that is not IEEE-exact.

The third goal comes first. Adding FP64 on top of backends that already
disagree about FP16 results would produce FP64 results that also disagree,
which defeats the purpose.

## 2. Current state (surveyed 2026-09-29)

### 2.1 Structural fit

The report that proposed this work is right about the structure:

- tiles are 512 bits, which is exactly 16 binary32 or 8 binary64 lanes;
- GPRs are 64 bits and hold a raw binary64 value exactly;
- the TACC bank is 2,048 bits, so 8 or 16 binary64 accumulator lanes fit;
- TMODE `EW` codes 6 and 7 are unassigned, and TMODE bit 3 is reserved and
  unread by every backend;
- `rtl/core/mp64_fp_exact.v` already provides bit-exact binary32 decode,
  RNE rounding, addition, and exact-product feedback, with full subnormal
  support and canonical NaN.

There are seven physical tile engines: four private to full cores and three
shared by the microcore clusters (`rtl/soc/mp64_soc.v:1310`,
`rtl/core/mp64_cluster.v:2207`).

### 2.2 Floating-point results differ between backends

| Behaviour | Python emulator | Native C++ | Hosted simulator | RTL |
|---|---|---|---|---|
| FP SUM, SUMSQ | host `sum()`, which is compensated summation in CPython 3.12+ and so depends on the interpreter version | falls back to Python; the unused C++ body is sequential binary32 | host `sum()` | balanced pairwise binary32 tree |
| FP DOT, DOTACC | sequential binary64 loop, one pack | sequential binary64 loop, one pack | sequential binary64 | same binary32 tree; DOTACC uses the level-3 subtrees |
| TMAC, TFMA | binary64 `a*b+c`, then binary32, then FP16 (not fused) | binary32 `float` arithmetic, possibly contracted by the compiler | binary64 `a*b+c` | FP16 multiply, then a separate FP16 add (two roundings) |
| TALU add/mul | binary64, then binary32, then FP16 | binary32 | binary64 | `mp64_fp16_alu` |
| Subnormal results | encoded, but the largest-subnormal carry is lost (`0x0017*0x5190` gives `0x0000`, not `0x0400`) | same bug | same bug, pinned by a test | MUL flushes subnormals to zero; FP32-to-FP16 narrowing flushes too |
| BF16 add/mul rounding | RNE via binary32 staging | RNE via binary32 staging | as Python | appears to truncate (rounds at the wrong bit) |
| FP MIN/MAX with ACC_ACC | ignores ACC_ACC | as Python | ignores ACC_ACC | adds the result to ACC0 |
| ACC1-3 after FP DOT/SUM | cleared | cleared | cleared | kept on ACC_ACC |
| EW 6/7 | treated as BF16 | treated as BF16, without the overflow preflight | rejected | treated as FP16; broadcast operand becomes 0; lane-shape paths use 32/64-bit lanes |

The FP16 encoder also stages every value through binary32 first, so it rounds
twice. No backend implements a correctly rounded fused multiply-add for any
format.

### 2.3 Oracles and tests

- The only exact integer oracle is in the emulator
  (`_decode_ieee_exact`, `_round_shift_rne`, `_round_exact_to_fp32`,
  `_tacc_fp32_add_product`, `emulator/megapad64.py:383-518`). Only TAMAC and
  the RTL vector generators use it. Its decoder is already parametric in
  exponent and fraction width.
- Host-float conversion code exists in three copies: `shared/fp.py`,
  `emulator/megapad64.py`, and `mp64_accel.cpp`.
- RTL is checked against golden vectors generated by the emulator
  (`rtl/sim/gen_fp_exact_vectors.py`, `gen_tamac_fp_vectors.py`). The legacy
  FP TALU/TMUL/TRED paths have no generated vectors, only a few hand-written
  cases in `tb_tile.v`. `mp64_fp16_alu.v` has no bench of its own.
- These tests pin current backend-specific behaviour and will change:
  `tests/test_native_mex_oracle.py:1872, 1903, 1935-1990`;
  `tests/simulator/test_kdos_buffer_fp.py:249, 277`;
  `tests/test_fp_formats.py:150-170`;
  `tests/simulator/test_kdos_buffer_tile.py:276-283`.
- `tests/test_megapad64.py::test_tile_fp` uses a `check()` helper that never
  asserts, so its failures do not fail the suite.

### 2.4 Encoding space

- All 16 primary opcode families are full. Scalar FP needs an F-prefix
  engine. F7 and FC-FF are unassigned.
- Unassigned F-prefixes currently latch as a general modifier and do not trap.
  RTL derives the REX register bits from any modifier value
  (`rtl/core/mp64_cpu.v:202-204`), so an unassigned prefix in front of an
  ordinary instruction silently changes its registers in RTL only.
- Extended tile space: `F8 E0` (extended TALU) uses functions 0-3 and leaves
  4-7 free. `F8 E1` and `F8 E2` are unassigned. `F8 E3 07` is reserved for a
  future narrowed TACC store (`docs/chip-math-update-handoff.md:2482`).
- TACC_STATUS packs `FORMAT_EW` in `[7:5]`, `FORMAT_SIGNED` in `[8]`, and
  `FORCE_PENDING` in `[9]`. A 4-bit format code does not fit without moving
  fields.
- The FLAGS register is `[S I G P V N C Z]`. No FP exception flags exist
  anywhere. Free CSR addresses include `0x0D-0x0F` and `0x26-0x2F`.

### 2.5 Software consumers

- BIOS: `FP16-MODE`, `BF16-MODE`, the tile words, and the TACC words.
- KDOS: `F.SUM`, `F.DOT`, `F.SUMSQ`, `F.ADD`, `F.MUL`, `BF.SUM`, `BF.DOT` and
  the `kf*` kernels (`kdos.f:3112-3216, 3587-3607`). They chain tiles with
  ACC_ACC, so they depend on the inter-tile rounding rule.
- Akashic: `math/fp16.f` and `fp16-ext.f` (scalar FP16 through tile lane 0,
  required by about 35 files); `math/fp32.f` (software binary32, required by
  audio, statistics, LEL, and the state tree); `math/simd.f` mode words. No
  Akashic code writes EW 6 or 7 or uses FP64.

## 3. Design rules for this work

1. **One definition, four implementations.** Every floating-point result is
   defined by an exact reference. Host evaluation order is never the
   definition.
2. **The exact reference is integer based.** A fast path may use host binary64
   only where it is provably identical to the exact result:
   - binary64 add, subtract, multiply, divide, and square root on the host are
     correctly rounded;
   - binary32 and narrower add, subtract, multiply, divide, and square root
     computed in binary64 and then rounded once to the target are correctly
     rounded, because 53 ≥ 2p + 2 for p ≤ 24;
   - binary64 FMA through Python 3.13 `math.fma` or C++ `std::fma` is
     correctly rounded.

   A narrower FMA done through binary64 can round twice, so it must use the
   exact path or an error-free transformation. The oracle test suite checks
   every fast path against the exact path. This is a speed-up that removes
   only provably redundant work.
3. **Native C++ is built with `-ffp-contract=off`.** Where it uses host
   floating point, it follows the same provable fast-path rules.
4. **No legacy preservation.** The project is unreleased. The FP16 PACK/BF16
   swap, the host-`sum` order, the old TACC_STATUS packing, and `shared/fp.py`
   are replaced, not kept beside the new code.
5. **The RTL describes the chip we want.** Physical unit counts are ordinary
   build parameters. FPGA board fit is not a design gate.

## 4. Decisions (confirmed 2026-09-29)

Every recommendation below was confirmed, including changing integer
MIN/MAX under ACC_ACC. `docs/floating-point.md` is the normative record.
Where it adds detail or refines a decision, it wins. Writing it produced
these refinements:

- **D8.** The cycle table is fixed in §10 of the spec. Divide and
  square-root latencies are fixed as data-independent constants by the phase
  that chooses their algorithm (Phase 7 for scalar, Phase 8 for tiles).
- **D9.** `TCVT` converts a contiguous region rather than a
  `TSRC0`/`TSRC1` pair. Widening by ratio `k` writes `k` tiles from `TDST`,
  and narrowing reads `k` tiles from `TSRC0`, so every source lane is
  converted for any width ratio. Only SS=0 is legal. Integer-to-integer and
  same-format conversions trap, because PACK/UNPACK cover the integer cases.
- **D10.** VSEL is unfinished in every backend today, and the backends
  disagree: Python and native return A, while RTL returns `msb(B) ? A : 0`.
  The spec defines it as `msb(M) ? A : B`, with M the old `[TDST]`. It is
  built in Phase 6 with `TCMP`.
- **D12.** Opcode numbers are assigned in spec §8.3. Static rounding modes
  are encoded in the low three bits of the FRND and FCVT-to-integer
  opcodes.
- **D15.** `FPCSR` is CSR `0x0D`.
- **D17.** The converted immediate is operand A and the tile is operand B, as
  the existing docs and Python already arrange integer splats.

**D1. TMODE.** `EW` becomes a 4-bit field in `[3:0]`, taking the reserved
bit 3.

| EW | Format | Lanes |
|---:|---|---:|
| 0 | U8/S8 | 64 |
| 1 | U16/S16 | 32 |
| 2 | U32/S32 | 16 |
| 3 | U64/S64 | 8 |
| 4 | FP16 | 32 |
| 5 | BF16 | 32 |
| 6 | FP32 | 16 |
| 7 | FP64 | 8 |
| 8-15 | reserved | — |

Bits `[4]`, `[5]`, and `[6]` keep their meanings. Bit 7 and bits above 7 stay
reserved for later growth.

- Any tile operation in a reserved format traps `IVEC_ILLEGAL_OP` before it
  touches memory.
- TMODE is 8 bits wide in every backend. Writes keep `[6:0]`; reserved bits
  read as zero. TCTRL gets the same rule for its defined bits.

**D2. TACC_STATUS repack.** Fields become:

| Bits | Field |
|---|---|
| `[8:5]` | `FORMAT_EW` |
| `[9]` | `FORMAT_SIGNED` |
| `[10]` | `FORCE_PENDING` |
| `[20:16]` | `OWNER` (unchanged) |

The other bits are unchanged.

**D3. Accumulation format.** `A(FP16) = A(BF16) = binary32` and
`A(FP32) = A(FP64) = binary64`.

- Legacy-ACC floating results are one `A` value in ACC0, zero-extended when it
  is binary32.
- FP32 DOT/SUM/SUMSQ therefore publish binary64.

**D4. Canonical reduction.** The existing RTL tree becomes the definition for
every float format.

- Leaves are the lanes widened exactly to `A`, or for DOT and SUMSQ each
  product rounded once to `A`. The product is exact for FP16 and FP32 inputs.
  It is rounded for BF16 at the binary32 range limits, and for FP64.
- Leaves are summed pairwise in lane order, (0,1), (2,3), …, then level by
  level, with one RNE rounding at every node.
- DOTACC chunk `k` is the subtree over its quarter of the lanes.
- With ACC_ACC, the result is `RN_A(ACC0 + tree)`. When ACC_ZERO is set, the
  tree result is written directly with no add, so a -0 result survives.
- Floating DOT, SUM, SUMSQ, and L1 always clear ACC1-3.
- MIN and MAX with ACC_ACC keep a running minimum or maximum against ACC0.
  Integer TRED MIN/MAX currently add under ACC_ACC
  (`emulator/megapad64.py:4876-4879`), which is not useful, so they change to
  a running minimum or maximum as well (confirmed).

**D5. NaN, zero, and subnormals.**

- Every arithmetic NaN result is the positive canonical quiet NaN of its
  format: `0x7E00`, `0x7FC0`, `0x7FC00000`, or `0x7FF8000000000000`.
- ABS, AND, OR, XOR, VSEL, SHUFFLE, and moves are raw bit operations and keep
  payloads.
- Subnormals are supported everywhere, with no flush-to-zero.
- TALU MIN/MAX propagate NaN and order -0 below +0 (IEEE 754-2019 `minimum`
  and `maximum`).
- TRED MIN/MAX/MINIDX/MAXIDX skip NaN lanes. An all-NaN tile gives the
  canonical NaN. Ties go to the lowest index.

**D6. Fused operations.** TFMA and TMAC round exactly once in every float
format. The existing unfused FP16 paths are replaced.

**D7. Physical datapath.** A new multi-format FMA unit computes one binary64
FMA, or two binary32 FMAs in split mode.

- Each engine has `P` units. `P` is an RTL parameter, and the production
  chip uses `P = 2`, so an FP32 or FP64 element-wise operation takes 4
  arithmetic beats.
- Reductions schedule the canonical tree over those units. The order never
  depends on `P`.
- FP16/BF16 keep 32 parallel lanes, but the lane unit is rewritten as a
  correct fused FP16/BF16 unit, replacing `mp64_fp16_alu`.
- The alternative is to route FP16/BF16 through the shared FMA units. That is
  smaller hardware, but half-precision ops become about 4x slower, and Akashic
  audio depends on them.

**D8. Timing model.** The emulator's cycle costs for FP32/FP64 come from the
`P = 2` schedule and are held in one shared constant table. Phase 1 fixes the
numbers. The strict-cycle transport charges beats exactly as for existing tile
operations.

**D9. Conversions.**

- **The TCVT instruction.** A new instruction, `TCVT` (`F8 E0`, function 6),
  converts from `TMODE.EW` to a target format held in function byte bits
  `[7:4]`, for any pair of formats, integer or float.
- **Widening and narrowing.** Widening writes `TDST` and `TDST+64`, as WMUL
  does. Narrowing reads `TSRC0` for the low lanes and `TSRC1` for the high
  lanes into one `TDST`.
- **Rounding.**
  - Float-to-float and int-to-float conversions round RNE.
  - Float-to-int truncates toward zero when TMODE bit 6 is 0 and rounds RNE
    when it is 1, reusing the existing rounding bit.
  - Out-of-range values saturate, and NaN converts to 0.
- **Float PACK and UNPACK are removed.** They trap in float formats, and
  integer PACK and UNPACK are unchanged.

**D10. Compare to mask.** A new instruction, `TCMP` (`F8 E0`, function 7),
writes an all-ones or all-zero lane mask for use with VSEL. The predicate is in
the function byte (EQ, NE, LT, LE, UNORD, …), and signed mode is used in
integer formats. It is recommended because filtering and masking are basic to
data analysis. It is optional.

**D11. Tile divide and square root.** `TDIV` and `TSQRT` (`F8 E0`, functions 4
and 5) are correctly rounded and defined only in float formats; integer formats
trap. They run iteratively in the FMA units. They are scheduled last and may be
deferred.

**D12. Scalar FP encoding.** A new self-contained engine prefix, `FC`:

- `FC op DR` is 3 bytes, where `DR` is `[Rd:4][Rs:4]` as in EXT.STRING;
- the three-operand forms are `FC op DR T` (4 bytes), where `T[4:0]` names
  `Rt` directly;
- a REX prefix extends Rd and Rs as for the other engines;
- the `op` byte is `[7:6]` format (00 FP32, 01 FP64, 10/11 reserved) and
  `[5:0]` operation;
- undefined operations trap;
- in the same decoder change, F7 and FD-FF become illegal instead of
  latching as silent modifiers.

The operations are:

- add, subtract, multiply, divide, square root;
- FMA (`Rd ← Rs×Rt + Rd`) and FMS (`Rd ← Rd − Rs×Rt`);
- minimum and maximum;
- compare to flags (`FCMP`);
- the Forth-style flag producers `FEQ`, `FLT`, and `FLE` (Rd ← -1 or 0);
- classify;
- round to integral with a static or dynamic rounding mode;
- conversions: int64/uint64 to and from float, FP32 to and from FP64, and
  FP32/FP64 to and from FP16 and BF16.

Sign operations use the integer ALU. Phase 1 assigns the opcode numbers.

**D13. Scalar values in GPRs.** A binary64 value uses the whole register.
A binary32 value uses the low 32 bits; results zero the upper 32 bits and
inputs ignore them.

**D14. FCMP flags.** Z = equal, G = greater, N = less, V = unordered, C = 0.
The existing EQ, NE, GT, MI, PL, VS, and VC branches then work unchanged.
`LE` is true for unordered operands, so code that must treat NaN specially
tests VS first; `FLE` gives the exact predicate.

**D15. FP control and status.** A new CSR, `FPCSR` (proposed `0x0D`), is
private per core; microcores keep shadows. Its fields are:

- `RM[2:0]`: RNE, RTZ, RDN, RUP, RMM;
- sticky flags `[8:4]`: NV, DZ, OF, UF, NX.

Scalar operations honour `RM` and set the flags. FP exceptions never trap,
which is the IEEE default. Tile operations are RNE-only and set no flags in
this plan. Tile flags can be added later as an OR of lane flags into the
issuing core's `FPCSR`.

**D16. Microcores.** Scalar FP uses one cluster-shared FP unit per cluster,
reached through the same request/done port pattern as MUL/DIV
(`rtl/core/mp64_cluster.v:777-804`), at +3 cycles. This keeps all 16 cores on
one ISA, as MEX already is. The alternative is to trap, like the microcore
Tier-2 bitfield operations.

**D17. Broadcast and immediate operands in float formats.**

- Broadcast uses the low 32 bits of Rn for FP32, all 64 bits for FP64, and
  the low 16 bits for FP16 and BF16.
- For `imm8` splat, the recommendation is to convert the unsigned
  immediate exactly to the lane format.

**D18. Lane shape.** In float formats, SHUFFLE, RROT, TRANS, POPCNT, and VSEL
use the format's real lane width: 16 bits for FP16/BF16, 32 for FP32, 64 for
FP64. VSHR, VSHL, and VCLZ trap in float formats.

may land in several commits, one per coherent green slice.

- **`docs/tile-engine.md`.** Updated with the 4-bit TMODE, the new extended

- **`docs/isa-reference.md`.** Updated with FLAGS/FCMP, the MEX float note,

### Phase 2 — Exact oracle and FP16/BF16 unification

This phase fixes the existing divergence before any new format is added.

1. **Shared exact module.** `shared/ieee_fp.py` covers binary16, bfloat16,
   binary32, and binary64. It provides:
   - decode and classify;
   - round-once from an exact `(sign, significand, exponent)` to any format,
     with RNE and, for scalar use, the other rounding modes;
   - add, subtract, multiply, FMA, divide, square root, conversions, min/max,
     compare, and the canonical tree.

   It replaces `shared/fp.py`, the conversion copies in
   `emulator/megapad64.py`, and the TAMAC-only oracle there.
2. **Oracle tests.** Named hard cases cover:
   - ties at every boundary, including the subnormal-to-normal carry;
   - overflow to infinity;
   - signed zero from cancellation;
   - NaN and infinity combinations, including `0 × ∞`;
   - BF16 range limits.

   Seeded random sweeps compare every fast path with the exact path. Where
   an independent check is useful, one is added (for example against
   `numpy` float32/float64 in the test environment only).
3. **Emulator and hosted simulator.** Move FP16/BF16 TALU, TMUL, and TRED onto
   the module. This covers:
   - the canonical tree;
   - fused TMAC and TFMA;
   - the ACC_ACC, ACC_ZERO, and ACC1-3 rules;
   - MIN/MAX under ACC_ACC;
   - the FP16 carry fix.

   Remove the `_exec_mex_direct` duplicate FP branches if they are not
   needed. Make `test_tile_fp` assert.
4. **Native C++.** Make SUM/SUMSQ native and bit-exact, keep fallbacks only
   for cases that are truly rare, and build with contraction off. Port FP TAMAC
   natively only if it is cheap; the Python fallback is correct.
5. **RTL.**
   - Replace `mp64_fp16_alu` with an IEEE-correct fused FP16/BF16 lane unit
     built from format-generic pieces factored out of `mp64_fp_exact.v`.
   - Apply the ACC rules and the MIN/MAX fix in `mp64_tile.v`.
   - Add a generator for FP16/BF16 TALU/TMUL/TRED golden vectors from the
     oracle, a bench for the new lane unit, and regeneration checks in
     `rtl/sim/Makefile`.
6. **Tests and docs.** Update the pinned tests listed in §2.3 to the new
   definition. Close non-determinism audit items H-2 (already fixed but not
   marked), H-3, H-4, and J-5.

KDOS words keep working because the inter-tile rule is still one rounding per
tile, but some expected values in their tests change.

### Phase 3 — Mode and state plumbing

- **TMODE.** Implement the 4-bit `EW` in all four backends, with the D1
  reserved-format traps and the TMODE/TCTRL width rule.
- **Format descriptors.** Replace every "all FP is 16-bit" shortcut
  (`elem_bytes = 2`, `ew >= EW_FP16`, `mode_fp = mode_ew[2]`, the BF16
  `else` branches) with one format descriptor table per backend. Each entry
  holds lane bytes, lane count, accumulation format, canonical NaN, and
  whether the format is float.
- **TACC_STATUS.** Apply the D2 repack. Widen `format_ew` to 4 bits through
  `mp64_tacc.v`, `mp64_tacc_transfer.v`, `mp64_soc.v`, and `mp64_cluster.v`.
- **Fail closed.** EW 6 and 7 are now defined formats, but every operation in
  them traps until Phase 4 or 5 implements it. This keeps each backend fail
  closed in the meantime.
- **BIOS and hosted words.** Add `FP32-MODE` and `FP64-MODE` to the BIOS and
  to hosted `core_words.py`, and update the dictionary docs.

### Phase 4 — FP32/FP64 element-wise tile operations

- **Element-wise operations.**
  - TALU ADD, SUB, MIN, MAX, ABS; AND, OR, and XOR are raw.
  - TMUL MUL, FMA, and MAC.
  - WMUL takes FP32 × FP32 to an exact binary64 product. FP64 WMUL traps.
- **Operands and lane shape.** Apply the broadcast and immediate rules of
  D17 and the lane-shape rules of D18.
- **RTL.**
  - Add the multi-format FMA unit, with its own bench and oracle vectors.
  - Add the `P` parameter.
  - Add a beat scheduler in `mp64_tile.v` modelled on the existing TAMAC
    beat logic (`tamac_beat_reg`, `mp64_tile.v:1733-1896`).
- **Timing.** Add the D8 cycle table to Python and C++.

### Phase 5 — FP32/FP64 reductions and TACC formats

- **Reductions.** TRED SUM, SUMSQ, L1, MIN, MAX, MINIDX, and MAXIDX, and TMUL
  DOT and DOTACC, publishing binary64. Reductions use the canonical tree
  scheduled over the FMA units.
- **TACC formats.**
  - EW 6: 16 binary64 lanes. Each TAMAC adds the exact FP32 product with
    one rounding. Active image 128 bytes.
  - EW 7: 8 binary64 lanes. Each TAMAC is a true FMA. Active image 64
    bytes.
  - Both use the FMA units. The TACC transfer rule that only EW 0 and 1 use
    bytes 128-255 still holds.
- **Tests.** Extend the TACC vector generators and benches.

### Phase 6 — Conversions and compares

- Implement `TCVT` (D9), `TCMP` (D10), and the new `VSEL` definition in all
  backends.
- Remove float PACK and UNPACK.
- Add BIOS and KDOS words for buffer conversion between formats.

### Phase 7 — Scalar FP unit

- **Engine and state.** Implement the `FC` engine (D12-D16) in the Python
  emulator, native C++ decode and DBT lowering, RTL full core, and RTL
  cluster. Include `FPCSR` and the F7/FD-FF traps.
- **Divide and square root.** These are iterative with a fixed documented
  latency, using the existing start/busy/done pattern
  (`rtl/prim/mp64_mul.v`, the divider in `mp64_cpu.v:2067-2130`).
- **Tools and words.**
  - Add assembler mnemonics to `asm.py`.
  - Add BIOS Forth words on cells; Phase 1 fixes the names.
  - The hosted simulator gets matching words bound to the oracle, since it
    models no instruction encodings.

### Phase 8 — Tile divide and square root (optional, D11)

Correctly rounded `TDIV` and `TSQRT` in FP16, BF16, FP32, and FP64. They are
iterative in the FMA units, and every backend is checked against the oracle.

### Phase 9 — Closure

- **Parity sweep.** Run one cross-backend parity sweep over every float
  operation and format using the generated vectors.
- **Docs.** Update the README resource table as an estimate only, the
  ROADMAP, and the audit.
- **Akashic handoff note.**
  - Software `fp32.f` can move to the scalar unit.
  - `fp16.f:189` adds binary32 bit patterns with an integer `+`.
  - The `simd.f` mode table needs FP32 and FP64.
  - That repository's work is its own vertical.
- **Final regression.** Run the physical Desktop journey once, because the
  hosted simulator changed.

## 6. Testing and resource rules

- **Entry points.** Use `make test-sequential TEST_PATH=… K=…`,
  `make test-simulator`, `make test-quick`, and the RTL leaf targets
  `make -C rtl/sim fp_exact|tile|tacc|tacc_cycles`. Direct `pytest` is
  blocked without `MP64_VIA_MAKE=1`.
- **Lightweight, run freely.** The oracle tests, `test_fp_formats.py`,
  `test_tacc_isa.py`, `test_native_mex_oracle.py`, the hosted simulator tile
  tests, and the RTL leaf benches.
- **Heavyweight, one at a time.** These run within the existing watchdog and
  RSS guards:
  - `test_system.py::TestKDOSFP16` and the BIOS TACC tests;
  - the RTL `cluster`, `tacc_soc`, `soc_smoke`, and `soc_elaborate` targets;
  - the physical Desktop journey.
- **Ask first.** Ask before running `test_tacc_contention.py`, which spawns
  workers, or any synthesis run.
- **While iterating, run narrow selectors only.** The Desktop journey is a
  final regression, never an iteration tool.

## 7. Defects found during the survey, not on this critical path

These are recorded here and left alone unless a phase cannot be correct
without fixing them.

- **RTL instruction length.** `instr_len` uses a generic `has_ext` flag, so a
  REX prefix in front of IMM may be given a 10-byte length
  (`rtl/pkg/mp64_cpu_funcs.vh:98-104`). This needs verification.
- **Unknown crypto units.** Full-core RTL runs EXT.CRYPTO units 3-F as a NOP,
  while Python and the microcores trap (`mp64_cpu.v:1745-1748`).
- **Divide timing.** Emulator DIV costs 4 cycles, while RTL takes about 65.
- **Docs out of step with code.**
  - Docs list WMUL/MAC/FMA at +1 cycle; the code charges +2.
  - `docs/tile-engine.md:502-505` says RTL does not implement TACC, which
    contradicts `docs/isa-reference.md`.
- **Unaligned tile addresses.** The backends still disagree on them
  (`docs/tile-engine.md:72-78`).
- **Unused `S` flag.** The FLAGS `S` bit is documented as sticky saturation
  but nothing sets it.
- **Unmasked CSRs in C++.** Native C++ does not mask SB, SR, SC, or SW on
  write.
- **Integer immediate splat.** Every backend copies the immediate into every
  byte, so a 16-bit lane receives `0x0505` for immediate 5. The docs say it
  adds a small constant to every element. RTL also places the splat in
  operand B, where Python and the docs place it in operand A. That only
  matters for non-commutative functions, and the forced function 0 is
  commutative for TALU and TMUL. Float formats get their own exact rule
  (D17).
- **Unassigned extended functions.** `F8` with TALU functions 4–7 does not
  trap in Python, which writes zero lanes. The other backends were not
  checked. Phases 6 and 8 give those functions
  meanings.
